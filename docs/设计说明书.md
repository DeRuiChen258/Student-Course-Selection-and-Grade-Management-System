# 第 1 章 需求分析

## 1.1 项目背景与目标

高校教务系统中的选课与成绩管理是数据库课程最典型的应用场景：数据对象清晰、约束关系密集、并发行为
可复现，又同时覆盖增删改查、视图、存储过程、触发器、事务、索引与权限等全部教学知识点。本系统面向
高校教务的选课业务，实现「学生—班级—院系」「教师—开课—课程」「学生—选课—成绩」三条主线的数据管理，
并用一套可脚本化回放的演示流程证明数据库对象真实生效。

本系统要回答的问题有三类：第一，教务基础数据如何用关系模型准确表达，并保证参照完整性与用户定义
完整性；第二，选课这一典型的并发写入场景，如何通过事务、行锁、唯一约束与触发器避免超额与重复；
第三，当数据规模从演示级（百行）增长到教学级（万行以上）时，索引如何影响查询计划与响应时间。

系统目标可归纳为三点：一是覆盖题目要求的全部功能（增加、修改、删除、查询，以及选课、退课、成绩录入
与修改、信息查询）；二是把课程知识点落成可验证的数据库对象（9 张表、4 个视图、3 个存储过程、
2 个函数、5 个触发器、16 个显式索引）；三是提供可复现的证据链，包括测试输出、并发验证、执行计划
对比与备份恢复记录。

## 1.4 安全与性能需求

安全需求包括四点：一是数据库账号最小权限，应用账号只拥有业务所需的增删改查与过程执行权限，
教师账号仅能修改成绩列，只读账号只能访问四个视图；二是口令不以明文存储，`sys_account` 保存
`盐$SHA-256(盐+口令)`；三是所有写操作使用参数化语句，避免 SQL 注入；四是关键写操作保留审计日志，
学生删除与信息修改均可追溯。

性能需求包括三点：一是演示数据下所有功能响应在毫秒级；二是万行规模下按班级、按学期、按开课的
代表查询必须命中索引，且相对全表扫描有明显优势；三是选课并发场景不允许出现超额，容量 1 的开课
被两人同时选课时必须恰好一人成功。

## 2.4 弱实体与多值属性处理

开课是依赖课程与教师存在的弱实体：它没有独立的业务标识，其唯一性由「课程 + 教师 + 学期」三元组
确定，因此在外键全部为 RESTRICT 的前提下，课程或教师被删除前必须先清理开课记录。

选课同样是依赖学生与开课存在的弱实体，且其属性随业务过程变化（成绩由空到有、状态由已选到已退）。
本设计把它建模为独立关系而非把成绩塞进学生表或课程表，理由是：成绩描述的是「某学生选修某开课」
这一事件，属于联系属性；若并入实体表，会出现同一学生多条成绩无法表达、课程表被学生数量膨胀等问题。

多值属性在本模型中不出现：学生联系方式只保留一个主号码与一个主邮箱，课程类型用枚举约束单值，
审计日志则用独立实体承担「一条记录多次变更」的历史信息，避免了在业务表中维护变长列表。

## 3.2 范式分析

第一范式（1NF）：所有关系的属性均为原子值，不存在重复组或数组。选课关系把「一个学生对多门课」
拆成多条元组，而不是在一条记录中保存课程列表；审计日志把多次变更拆成多行，避免变长明细。

第二范式（2NF）：每个关系都已达到 1NF，且不存在非主属性对候选键的部分函数依赖。选课关系的候选键
是 (student_id, offering_id)，其非主属性 enroll_time、score、score_time、status 均依赖完整的候选键，
不依赖其中任何一部分；开课关系的候选键是 (course_id, teacher_id, semester)，capacity、classroom、
open_time 同样依赖完整候选键。

第三范式（3NF）：不存在非主属性对候选键的传递函数依赖。以学生关系为例，student_no → student_id →
(student_name, gender, birth_date, class_id, ...)，且 student_no 与 student_id 都是候选键，
因此不构成对非候选键的传递依赖；班级名称依赖 class_id 而不是 student_id，因此被拆到班级关系中；
院系名称同理被拆到院系关系。教师职称、院系归属均直接依赖 teacher_id。

受控冗余的说明：开课关系的 enrolled_count 可以从选课关系聚合得到，属于刻意的反范式设计。
保留该列的理由是：选课与退课发生在高并发路径上，每次都在 enrollment 上做 COUNT(*) 聚合会带来
额外的锁竞争与统计误差；改为由 AFTER INSERT / AFTER UPDATE 触发器在同一事务内原子维护，
并用 CHECK (enrolled_count <= capacity) 兜底，可以得到「读快、写准」的效果。一致性风险由三处
共同覆盖：应用层在事务中先锁行再判断、触发器在写入前后联动计数、CHECK 约束在数据库端拒绝越界。

## 3.3 完整性约束设计

@table 表 3-2 完整性约束与实现
| 类别 | 覆盖对象 | 实现 | 设计理由 |
| --- | --- | --- | --- |
| 实体完整性 | 9 张表 | 全部定义主键 | 每行可唯一标识 |
| 替代键唯一 | 学号、工号、课程代码、班级代码、院系代码与名称、账号名 | UNIQUE 约束 | 业务键不允许重复 |
| 业务唯一 | 开课三元组、选课二元组 | uk_offering、uk_enroll | 防重复开课与重复选课 |
| 参照完整性 | 11 个外键 | 基础数据 RESTRICT，学生删除 CASCADE，班主任 SET NULL | 误删基础数据被拒绝，删学生自动清理选课 |
| 用户定义完整性 | 学分、学时、容量、成绩、年级、角色绑定 | 7 个 CHECK 约束 | 值域在数据库端强制 |
| 枚举完整性 | 性别、学籍状态、课程类型、角色、日志动作 | ENUM | 取值集合固定且可读 |

关于账号绑定一致性的实现需要说明：`sys_account` 需要保证「STUDENT 必须绑定学生且不绑定教师、
TEACHER 必须绑定教师且不绑定学生、ADMIN 两者皆空」。MySQL 8 不允许在带 ON DELETE CASCADE 外键的
列上直接写 CHECK 表达式，因此本设计引入虚拟生成列 `bind_ok`（由角色与两个外键列派生）并对该列
建立 CHECK 约束，从而在保留级联删除语义的同时实现绑定一致性校验。

| v_student_transcript | 成绩单需要等级与绩点，Java 侧也要一致 | 用 CASE WHEN 实现与 GradeLevel 完全一致的换算 |
| v_course_stat | 报表需要选课人数、均分、最高/最低分、不及格人数 | 聚合 + COUNT/AVG/MAX/MIN + 条件求和 |

视图的作用不只是简化查询：它同时是权限控制的边界。`edu_teacher`、`edu_student`、`edu_readonly`
三个账号只被授予视图的 SELECT 权限，因此他们看到的是经过裁剪的列集合，无法直接访问底层业务表。

存储过程与应用层事务是「并行双实现」关系：应用层用 JDBC 的 Tx 模板完成同样的校验与写入，
供菜单与测试使用；存储过程则保证绕开应用直接操作数据库时（例如运维脚本、其他语言客户端）
仍然安全。两者的校验规则与错误码一一对应，避免出现「应用能拦、数据库拦不住」的漏洞。

## 3.6 触发器设计

@table 表 3-5 触发器清单
| 触发器 | 时机与事件 | 职责 |
| --- | --- | --- |
| trg_enrollment_bi | BEFORE INSERT ON enrollment | 开课不存在、名额已满、重复选课 → SIGNAL 45000 |
| trg_enrollment_ai | AFTER INSERT ON enrollment | 已选人数 +1（仅当状态为「已选」） |
| trg_enrollment_bu | BEFORE UPDATE ON enrollment | 成绩越界拒绝；成绩变化时刷新 score_time |
| trg_enrollment_au | AFTER UPDATE ON enrollment | 状态在「已选」与「已退」之间转换时维护已选人数 |
| trg_student_ad | AFTER DELETE ON student | 向 audit_log 写入一条 DELETE 记录（含学号与操作者） |

为什么触发器与应用层要同时校验：应用层校验负责给出可读错误码与友好提示，但它只覆盖本程序的执行
路径；数据库端触发器覆盖所有写入路径，包括手工 SQL、导入脚本与其他客户端。两者叠加才能既保证
体验又保证安全，这就是「双保险」。成绩时间戳之所以放在 BEFORE UPDATE 触发器中维护，是因为
MySQL 不允许在同一个表的 AFTER UPDATE 触发器里再更新该表本身，BEFORE 触发器可以直接修改
待写入的新值，是唯一正确的实现位置。

# 第 4 章 物理结构设计

## 4.1 存储引擎与字符集

9 张表全部使用 InnoDB 引擎，理由是：只有 InnoDB 同时提供事务、行级锁、外键与崩溃恢复，
而本系统的选课、退课、成绩写入都要求事务与行锁，参照完整性也依赖外键。字符集统一为 utf8mb4、
排序规则 utf8mb4_0900_ai_ci，保证中文姓名、课程名与全角符号正确存储，同时兼容 emoji 与生僻字。
时区在 JDBC 连接串中固定为 Asia/Shanghai，避免成绩时间与选课时间出现时区漂移。

## 4.2 数据类型选择

@table 表 4-1 主要字段的数据类型选择
| 字段 | 类型 | 选择理由 |
| --- | --- | --- |
| student_no | CHAR(12) | 定长数字串，等值查询为主，定长比变长更省索引空间 |
| student_name / course_name | VARCHAR(30) / VARCHAR(60) | 中文姓名与课程名长度有限，留足余量即可 |
| credit | DECIMAL(3,1) | 学分有一位小数，浮点会产生精度误差 |

索引设计的取舍：唯一索引承担业务键防重，是正确性要求；普通索引只服务于高频查询。
`idx_enroll_offering(offering_id, score)` 是典型的覆盖索引，因为按开课查成绩分布只需要这两列，
查询可以完全在索引中完成，无需回表。审计日志同时建立时间索引与「表名 + 时间」复合索引，
是因为排障时既可能按时间浏览，也可能按表名过滤。所有索引都基于真实查询建立，没有为了数量而
随意堆砌：学生姓名的模糊查询（`LIKE '%关键字%'`）无法命中 B+ 树，因此没有为该列建立无效索引，
而是通过分页与条件收窄控制扫描量。

## 4.4 执行计划与索引效果验证

第一组证据来自确定性演示数据（20 名学生、15 条开课、82 条选课）：

@table 表 4-3 小数据集下的执行计划（EXPLAIN）
| 代表查询 | type | key | rows | Extra |
| --- | --- | --- | --- | --- |
| 按班级查学生 `WHERE class_id=1` | ref | idx_student_class | 6 | NULL |
| 按学期查开课 `WHERE semester='2026-2027-1'` | ref | idx_offering_semester | 12 | Using index condition |
| 按开课查成绩分布 `WHERE offering_id=3 GROUP BY score` | ref | idx_enroll_offering | 10 | Using index（覆盖索引） |

三条查询全部走索引，type 均为 ref，且第三条使用了覆盖索引。这与设计预期一致：小数据量下索引的
收益主要体现在「精确命中而非全表扫描」，扫描行数与结果行数同量级。

第二组证据来自开源大数据集（导入后学生 28805、开课 135、选课 32675），对同一批查询分别执行
正常计划与 `IGNORE INDEX` 强制全表扫描：

@table 表 4-4 大数据集下的命中索引与全表扫描对比
| 代表查询 | 计划 | type | key | 预估 rows | Extra |
| --- | --- | --- | --- | --- | --- |
| 按班级查学生 | 命中索引 | ref | idx_student_class | 6 | NULL |

| 按开课查成绩分布 | IGNORE INDEX | ALL | NULL | 32884 | Using where; Using temporary |

进一步用 `EXPLAIN ANALYZE` 读取真实执行时间（MySQL 8 的执行计划分析）：

```text
-- 命中覆盖索引
-> Aggregate: avg(enrollment.score), count(0) (cost=1.25 rows=1) (actual time=0.0216..0.0217 rows=1 loops=1)
   -> Covering index lookup on enrollment using idx_enroll_offering (offering_id=5)

-- 强制全表扫描
-> Aggregate: avg(enrollment.score), count(0) (cost=3337 rows=1) (actual time=3.13..3.13 rows=1 loops=1)
   -> Filter: (enrollment.offering_id = 5) (cost=3313 rows=3288)
      -> Table scan on enrollment
```

同一查询命中覆盖索引时实际耗时 0.0217 毫秒，强制全表扫描时 3.13 毫秒，相差约 144 倍；
预估代价从 1.25 上升到 3337。可以得出的结论是：本项目在选课表上建立的覆盖索引，把「按开课统计
名单与成绩」这一高频报表查询从全表扫描降级为索引区间扫描，数据量越大收益越明显。

# 第 5 章 应用系统设计

## 5.1 分层架构

![图 5-1 系统分层架构与异常流](docs/figs/architecture.png)

系统分为四层：表现层（ui/console）负责菜单渲染与输入校验；业务层（service）负责业务规则、
事务边界与错误码映射；数据访问层（dao）负责参数化 SQL 与结果集映射；数据库层（MySQL）
负责存储、约束与过程/触发器。层间依赖单向向下，表现层不出现任何 SQL，数据访问层不出现任何
业务判断，这条边界由目录结构与代码评审共同保证。

事务边界的划法：只有业务层可以开启事务，事务只包裹数据库操作，绝不包含输入输出等待。
选课、退课、成绩写入、学生增删改、容量调整等写操作全部通过 `Tx.runInTx` 执行，
回调内抛出异常即整体回滚。

## 5.5 典型时序

选课成功路径：表现层收集学号与开课号 → 业务层开启事务 → 按学号读取学生（不存在抛 E002，
非在读抛 E001）→ 以 `FOR UPDATE` 锁定开课行（不存在抛 E003）→ 查询该生是否已有选课记录
（已选抛 E004）→ 比较已选人数与容量（满员抛 E005）→ 插入选课记录 → 触发器把已选人数加一 →
提交事务 → 表现层打印「选课成功：姓名 -> 课程代码（已选 x/y）」。

选课失败路径与成功路径共用同一条主线，差别只在判定点：任一校验不通过时抛出携带错误码的
`BizException`，事务模板捕获后回滚，表现层把错误码与中文说明打印给用户，并在 logs/app.log
写入一条 WARN 记录。因此失败路径既不留下半成品数据，也不会污染已选人数。

退课时序与之对称：锁定选课记录后先判断成绩是否为空（非空抛 E006），再把状态改为「已退」，
触发器回补已选人数。删除学生时则先批量把该生的在选记录置为「已退」释放名额，再删除学生行，
由外键级联清理选课记录，并由触发器写入审计日志。

# 第 6 章 关键功能实现

## 6.1 选课事务与并发控制

选课是最能体现数据库原理的功能：它同时涉及事务、行锁、唯一约束、容量校验与计数联动。
实现顺序为「先锁行、再校验、后写入」。

![图 6-1 选课业务流程图（含事务边界与异常分支）](docs/figs/enroll_flow.png)

图 6-1 的关键节点：进入事务后先用 `SELECT ... FOR UPDATE` 锁定开课行，这一步把并发的两个选课
请求串行化；随后依次校验学生状态、重复选课与容量；通过后插入选课记录，由 AFTER INSERT 触发器
在同一个事务内把已选人数加一；任何分支失败都整体回滚。

业务层核心代码如下（src/main/java/edu/scut/db/service/EnrollmentService.java，节选）：

```java
public String enroll(String studentNo, Integer offeringId) {
    return tx.runInTx(connection -> {
        Student student = studentDao.findByNo(studentNo);
        if (student == null) {
            throw BizException.of(ErrorCode.E002, "学号 " + studentNo + " 不存在");
        }
        if (!"在读".equals(student.getStatus())) {
            throw BizException.of(ErrorCode.E001, "学籍状态为「" + student.getStatus() + "」，不能选课");
        }
        // 行锁必须放在事务内，否则锁在语句结束后立即释放
        CourseOffering offering = offeringDao.findByIdForUpdate(connection, offeringId);
        if (offering == null) {
            throw BizException.of(ErrorCode.E003, "开课号 " + offeringId + " 不存在");
        }
        Enrollment existing = enrollmentDao.findByStudentAndOffering(connection,
                student.getStudentId(), offeringId);
        if (existing != null && "已选".equals(existing.getStatus())) {
            throw BizException.of(ErrorCode.E004, "该生已选此开课，不能重复选课");
        }
        if (offering.getEnrolledCount() >= offering.getCapacity()) {
            throw BizException.of(ErrorCode.E005, "开课 " + offeringId + " 名额已满");
        }
        enrollmentDao.insert(connection, student.getStudentId(), offeringId);
        return "选课成功：" + student.getStudentName() + " -> " + offeringId;
    });
}
```

计数为什么交给触发器：如果应用层插入选课记录后再手工执行 `UPDATE ... SET enrolled_count =
enrolled_count + 1`，一旦应用漏写或异常中断，就会与真实选课行数不一致；把计数维护写成
AFTER INSERT / AFTER UPDATE 触发器后，所有写入路径（应用、存储过程、导入脚本、手工 SQL）
都会自动维护计数，并在同一事务内提交或回滚。容量上限再由 `CHECK (enrolled_count <= capacity)`
兜底，形成「触发器联动 + 约束兜底」的闭环。

并发验证结果（EnrollmentConcurrencyTest，容量为 1 的开课被两个连接同时抢选）：

```text
[PASS] EnrollmentConcurrencyTest (11 ms)
```

用例断言两点：两个并发请求恰好一个成功、另一个收到 E005；并发结束后
`enrolled_count` 恰好等于 `capacity`。这证明行锁与触发器在真实并发下不会超额。

## 6.2 成绩录入的双保险校验

成绩写入涉及三条规则：区间 0–100、必须已选该课、写入或修改要刷新时间戳。实现分布在三层。

```java
public String saveScore(String studentNo, Integer offeringId, BigDecimal score) {
    if (!Validators.isScore(score)) {
        throw BizException.of(ErrorCode.E007, "成绩必须在 0 到 100 之间");
    }
    return tx.runInTx(connection -> {
        Student student = studentDao.findByNo(studentNo);
        Enrollment enrollment = enrollmentDao.findByStudentAndOffering(connection,
                student.getStudentId(), offeringId);
        if (enrollment == null || !"已选".equals(enrollment.getStatus())) {
            throw BizException.of(ErrorCode.E001, "该生未选开课 " + offeringId);
        }
        enrollmentDao.updateScore(connection, enrollment.getEnrollmentId(), score);
        return "成绩保存成功：" + score;
    });
}
```

## 6.3 GPA 与统计报表 SQL

绩点换算规则在 Java 与 SQL 两侧保持一致：A(90–100)=4.0、B(80–89)=3.0、C(70–79)=2.0、
D(60–69)=1.0、F(<60)=0。Java 侧由 `model/enums/GradeLevel` 实现，SQL 侧由视图
`v_student_transcript` 的 CASE WHEN 实现。

GPA 排名使用窗口函数一次性给出名次：

```sql
SELECT ROW_NUMBER() OVER (ORDER BY t.gpa DESC, t.student_no) AS rk, t.student_no,
       t.student_name, t.gpa, t.credits, t.fails
FROM (
    SELECT s.student_no, s.student_name,
           ROUND(SUM(x.gp * x.credit) / SUM(x.credit), 2) AS gpa,
           SUM(x.credit) AS credits,
           SUM(CASE WHEN x.score < 60 THEN 1 ELSE 0 END) AS fails
    FROM (SELECT e.student_id, c.credit, e.score,
                 CASE WHEN e.score >= 90 THEN 4.0 WHEN e.score >= 80 THEN 3.0
                      WHEN e.score >= 70 THEN 2.0 WHEN e.score >= 60 THEN 1.0
                      ELSE 0.0 END AS gp
          FROM enrollment e
          JOIN course_offering o ON o.offering_id = e.offering_id
          JOIN course c ON c.course_id = o.course_id
          WHERE e.status = '已选' AND e.score IS NOT NULL) x
    JOIN student s ON s.student_id = x.student_id
    GROUP BY s.student_id, s.student_no, s.student_name) t
ORDER BY t.gpa DESC, t.student_no LIMIT ?;
```

课程统计直接读取视图 `v_course_stat`，它用一条聚合查询同时给出选课人数、平均分、最高分、最低分与
不及格人数；不及格率在 Java 侧由 DTO 计算（`failCount / enrolledCount × 100%`，保留两位小数）。

## 8.2 设计亮点

第一，事务与触发器协同维护冗余计数。选课与退课在行锁保护下完成校验，计数由触发器在同一事务内
维护，并由 CHECK 约束兜底，三者形成闭环，既保证了并发正确性，也避免了应用层漏写导致的数据漂移。

第二，存储过程与应用服务双实现。同一套业务规则在 Java 服务与数据库过程中各实现一次，
错误码一一对应，既能给出友好提示，又能防止绕过应用直接写库造成脏数据。

第三，索引设计有据可依。三条代表查询在小数据集与大数据集下都给出执行计划，
并用 `IGNORE INDEX` 强制对照全表扫描，覆盖索引带来的实际差异达到约 144 倍，
结论可复现而不是估算。

第四，权限设计落到账号与视图。教师账号只能读三个视图并更新成绩列，学生与只读账号只能是视图查询，
越权操作返回 ERROR 1142，权限矩阵在数据库端与应用端同时生效。

第五，数据集合规且可复现。开源数据集标注了名称、来源、许可、获取日期、行数、字段映射与脱敏规则，
下载脚本带 sha256 校验，导入脚本「先更新后插入」保证幂等，并在导入前后各备份一次。

## 8.3 不足与改进方向

一是未使用连接池。当前实现为单连接复用，演示场景下响应很快，但在真实教务系统的高并发场景中
需要引入 HikariCP 等连接池并重新设计事务边界。二是未做 Web 化与图形界面，界面是题目允许的
控制台字符菜单，交互效率有限。三是批量成绩导入是逐条事务，缺少合并提交与失败重试策略。
四是报表为实时聚合，数据量继续增长后应考虑物化汇总表或按学期预计算。五是审计日志只覆盖学生
删除与信息修改，后续可扩展到全部关键表的变更留痕。

## B.2 选课前置校验触发器（sql/05_triggers.sql）

```sql
CREATE TRIGGER trg_enrollment_bi BEFORE INSERT ON enrollment
FOR EACH ROW
BEGIN
    DECLARE v_capacity SMALLINT DEFAULT NULL;
    DECLARE v_enrolled SMALLINT DEFAULT 0;
    DECLARE v_dup INT DEFAULT 0;

    SELECT capacity, enrolled_count INTO v_capacity, v_enrolled
    FROM course_offering WHERE offering_id = NEW.offering_id;
    IF v_capacity IS NULL THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'E003 开课不存在';
    END IF;
    IF v_enrolled >= v_capacity THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'E005 名额已满';
    END IF;
    SELECT COUNT(*) INTO v_dup FROM enrollment
    WHERE student_id = NEW.student_id AND offering_id = NEW.offering_id;
    IF v_dup > 0 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'E004 重复选课';
    END IF;
END
```

## B.3 选课存储过程（sql/04_procedures.sql，节选）

```sql
-- 选课：行锁后校验并写入，计数由触发器联动
CREATE PROCEDURE p_enroll_student(
    IN  p_student_no VARCHAR(12),
    IN  p_offering_id INT,
    OUT p_code INT,
    OUT p_msg VARCHAR(100)
)
BEGIN
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        SET p_code = 40099, p_msg = '数据库异常，已回滚';
    END;
    SET p_code = 0, p_msg = 'OK';
    START TRANSACTION;
    SELECT student_id, status INTO v_student_id, v_status
    FROM student WHERE student_no = p_student_no;
    SELECT capacity, enrolled_count INTO v_capacity, v_enrolled
    FROM course_offering WHERE offering_id = p_offering_id FOR UPDATE;
    IF v_capacity IS NULL THEN
        SET p_code = 40003, p_msg = '开课不存在';
    ELSEIF v_enrolled >= v_capacity THEN
        SET p_code = 40005, p_msg = '名额已满';
    ELSE
        INSERT INTO enrollment (student_id, offering_id) VALUES (v_student_id, p_offering_id);
    END IF;
    IF p_code = 0 THEN COMMIT; ELSE ROLLBACK; END IF;
END
```

## B.4 事务模板（db/Tx.java，节选）

```java
public <T> T runInTx(SqlFunction<Connection, T> work) {
    Connection connection = provider.getConnection();
    connection.setAutoCommit(false);
    try {
        T result = work.apply(connection);
        connection.commit();
        return result;
    } catch (SQLException | RuntimeException e) {
        connection.rollback();
        throw e instanceof RuntimeException ? (RuntimeException) e
                : new DataAccessException("事务执行失败并已回滚：" + e.getMessage(), e);
    } finally {
        connection.setAutoCommit(true);
    }
}
```
