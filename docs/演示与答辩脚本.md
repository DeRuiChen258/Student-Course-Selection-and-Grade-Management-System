# 现场演示与答辩脚本（10 分钟版）

## 一、演示前 2 分钟准备

```bash
cd 学生选课与成绩管理系统
bash scripts/init_db.sh -u edu_app -p      # 还原演示数据：表=9 视图=4 触发器=5 学生=20 选课=82
bash scripts/build.sh                      # 编译：out/classes 61 个 class
bash scripts/run.sh                        # 进入控制台主菜单
```

演示顺序建议先看菜单总览（14 个二级菜单一次展开），再按 F01→F16 走主流程，最后演示异常与数据库对象。

## 三、数据库对象演示（答辩加分项）

```bash
# 对象数量一次性核对
mysql -u edu_app -p edu_system -e "
SELECT (SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='edu_system' AND table_type='BASE TABLE') AS 表,
       (SELECT COUNT(*) FROM information_schema.views WHERE table_schema='edu_system') AS 视图,
       (SELECT COUNT(*) FROM information_schema.triggers WHERE trigger_schema='edu_system') AS 触发器,
       (SELECT COUNT(*) FROM information_schema.routines WHERE routine_schema='edu_system') AS 例程;"

# 越权演示（教师账号不能改学生表）
mysql -u edu_teacher -p edu_system -e "UPDATE student SET phone='x' WHERE student_no='202301010001';"
# 预期：ERROR 1142 (42000): UPDATE command denied ... for table 'student'

# 存储过程演示（满员返回 40005）
mysql -u edu_app -p edu_system -e "CALL p_enroll_student('202301010003', 1, @c, @m); SELECT @c, @m;"

# 索引对比演示
mysql -u edu_app -p edu_system -e "EXPLAIN SELECT score, COUNT(*) FROM enrollment WHERE offering_id=5 GROUP BY score;"
mysql -u edu_app -p edu_system -e "EXPLAIN SELECT score, COUNT(*) FROM enrollment IGNORE INDEX (idx_enroll_offering) WHERE offering_id=5 GROUP BY score;"
```

## 四、常见提问与标准回答（10 问）

1. **为什么选课表要单独建表，而不是把成绩放在学生表里？**
   成绩描述的是「某学生选修某开课」这一事件的属性，属于联系属性。若并入学生表，一个学生多条成绩
   无法表达；并入课程表则会被选课人数膨胀。独立表还能用 UNIQUE(student_id, offering_id) 直接防重复选课。

2. **为什么已选人数要冗余存储？会不会不一致？**
   它是刻意的反范式：选课是高频并发写，每次聚合 COUNT 会放大锁竞争。一致性由三层保证：
   事务内行锁校验、AFTER INSERT/UPDATE 触发器原子维护、CHECK (enrolled_count <= capacity) 兜底。

3. **并发选课会不会超额？**
   不会。选课前先 `SELECT ... FOR UPDATE` 锁定开课行，两个并发请求被串行化，第二个人看到的是更新后的
   已选人数。并发测试用两个独立连接抢容量为 1 的开课，结果恰好一人成功、一人收到 E005。

4. **为什么触发器里还要再校验一次，应用层不是已经校验了吗？**
   应用层只覆盖本程序的写入路径。手工 SQL、导入脚本、其他客户端都会绕过应用层，触发器是数据库端的
   最后一道闸门。二者构成双保险，且触发器抛出的错误码与应用层一致，提示不会互相矛盾。

5. **为什么成绩时间戳放在 BEFORE UPDATE 触发器？**
   MySQL 不允许在同一个表的 AFTER UPDATE 触发器里再更新该表，否则会报「表已被使用」。
   BEFORE 触发器可以直接修改 NEW.score_time，是唯一正确且不需要额外语句的实现方式。

6. **学号、工号为什么用 CHAR 而不是 VARCHAR？**
   它们都是定长数字串，且以等值查询为主，CHAR(12) 与 CHAR(8) 在索引中更紧凑；同时用正则校验
   长度与字符集，避免出现前导空格等脏数据。

7. **视图在权限控制里起什么作用？**
   教师、学生、只读三类账号只被授予视图的 SELECT 权限，看不到底层业务表的全部列，
   教师账号另外只被授予 enrollment 表的 (score, score_time) 列更新权限，从而实现最小权限。

8. **开源数据集是怎么用的，会不会影响测试稳定性？**
   数据集只用于分页、索引对比与统计演示，测试与冒烟脚本一律跑在 07 号脚本的确定性小数据上。
   导入脚本「先更新后插入」，连续执行三次行数不变，导入前后各备份一次。

9. **如果换一台机器怎么跑起来？**
   按 README 的五步运行法：sudo 执行 00 建库脚本、复制并填写配置、`init_db.sh` 建对象与演示数据、
   `build.sh` 编译（需先放好 JDBC 驱动）、`run.sh` 运行。没有网络时用 `--generate 12000` 生成合成数据。

10. **这个系统的已知不足是什么？**
    未使用连接池、未做 Web 化、批量导入逐条事务、报表实时聚合、审计范围有限。
    这些在说明书第 8.3 节都有说明与改进方向。

## 五、演示失败时的兜底

| 现象 | 处理 |
| --- | --- |
| 数据库连不上 | 检查 `config/db.properties` 的 host/port，确认 MySQL 服务运行 |
| 数据被改乱 | `bash scripts/init_db.sh -u edu_app -p` 一键还原演示数据 |
| 演示学生已存在 | 先执行 `1 学生管理 → 3 学生信息删除` 删除 202301019999 |
| 编译报驱动缺失 | 按 `lib/README.md` 下载驱动后重试 |
| 报表为空 | 确认执行过 07 号脚本（init_db.sh 会自动执行） |
